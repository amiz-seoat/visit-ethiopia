# Project completion audit

Date: 2026-11-27. Scope: the whole repository (`frontend/`, `backend/`, `prisma/`, deployment configuration) and the live hosting accounts.

## 1. Starting point

| Area | What was found |
|---|---|
| Architecture | Express (ESM) API, React/Vite/TS SPA, and a half-finished migration from MongoDB to PostgreSQL/Prisma behind `DATABASE_MODE`, `CATALOG_DB` and `SKIP_MONGO` switches. The Prisma path was functionally complete for identity, tours, hotels, transport, bookings, payments, refunds and provider workspaces, with suites for each. |
| Production | Several old deployments: two Vercel "backend" projects returning 500, a Render service, and a Vercel frontend whose hidden `VITE_API_BASE_URL` pointed to one of the broken backends. Production still targeted MongoDB Atlas. |
| Payments | Mock provider only. The state machine was solid: CAS transitions, attempts, de-duplicated webhook events, refunds. No real gateway. |
| Tests | 236 of 237 Prisma checks passing. One suite needed a fresh seed. |
| Security | A **MongoDB Atlas credential was committed** in `frontend/.env` (commit `1c6c87e`) of the public repository. The CORS allow-list had a hard-coded Vercel origin. No auth-specific rate limit. The error handler logged `NODE_ENV` and hung requests when it was unset. |
| Bugs | See §3. Several were only visible once production ran Prisma-only. |

## 2. Decisions

1. **Production runs PostgreSQL only** (Neon free tier). Mongo stays behind `DATABASE_MODE=mongo` as a legacy path and still passes its regression battery. It's not deleted in this pass, to keep the change reviewable.
2. **Chapa** is the payment gateway. It's Ethiopian, supports ETB and mobile money, and has a test mode. Verification against Chapa's API is the **only** source of truth. Browser redirects never confirm payments.
3. **Demo payments stay available** in production only through an explicit `ALLOW_MOCK_PAYMENTS=true` flag, labelled as demo in the UI. Without Chapa keys or that flag, the API refuses to create bookings (503) rather than taking bookings it can't collect payment for.
4. **No business policies were invented.** Refund percentages and cutoffs keep their existing configurable defaults. No-show refunds, provider-initiated cancellation and payouts are listed as open decisions.
5. **Hosting:** Vercel (frontend), Render Blueprint (API), Neon (database). All free tier. No paid resources were created.

## 3. What was completed

### Production database and backend
- Neon project created. All 7 Prisma migrations applied with `migrate deploy`. Idempotent demo content seeded: 5 destinations, 3 approved providers, 4 tours with 32 departures, 3 hotels with room inventory, 1 coach operator with 3 routes and seat inventory, plus a restaurant and news.
- The seed creates **no usable logins** unless the operator supplies passwords through environment variables.
- `render.yaml` rewritten:
  - Build: Prisma generate, then `migrate deploy`. Start with `npm start`. Health check on `/health`.
  - Non-secret config is in the file. Secrets are `sync: false`. JWT and mock-webhook secrets are generated by Render.
- `server.js`:
  - validates configuration at startup and names missing variables, never their values;
  - graceful shutdown;
  - `unhandledRejection` logging;
  - a reconciliation scheduler.
- `/health` (liveness) and `/health/ready` (database check).
- Request logging, a production rate limit, and a stricter auth rate limit.
- Error handler normalises Prisma and body-parser errors and never leaks stack traces in production.

### Payments: Chapa
- `ChapaPaymentProvider`:
  - initialize and verify;
  - HMAC-SHA256 webhook signatures (either header accepted);
  - refund;
  - strict amount and currency mapping;
  - swappable HTTP layer for tests.
- `chapaCheckoutService`:
  - owner- or admin-only checkout;
  - server-generated `tx_ref` for each attempt;
  - reuse of a pending link within 10 minutes;
  - verify on return, callback, webhook and reconciliation;
  - amount, currency and reference matching;
  - mismatches are flagged;
  - failed attempts are retryable;
  - late payments after hold expiry are flagged for refund review.
- New endpoints:
  - `GET /payments/config`
  - `POST /payments/:id/checkout`
  - `POST /payments/:id/verify`
  - `GET /payments/chapa/callback`
  - `POST /payments/webhooks/chapa`
- The `PaymentProvider` enum gained `chapa` through an additive migration.
- Frontend:
  - "Pay with Chapa" button;
  - verification polling on return;
  - honest "Confirm demo payment" labelling.

### Integration and essential flows
- The frontend API base comes from a committed public `VITE_API_URL`. A production build fails without an API URL.
- A 401 clears the session and redirects to the login page with a safe, relative-only `redirect` parameter.
- `vercel.json` adds the SPA rewrite, asset caching and security headers.
- Email:
  - SMTP or Gmail transport;
  - background sending;
  - booking-confirmation email;
  - verification links redirect to the frontend;
  - production without email auto-verifies signups (documented).

### Bugs fixed
- **Reconciliation in Prisma mode called Mongoose models.** `Booking.findById` and `Refund.findOne` meant stale unpaid bookings were never expired and their inventory was never released.
- **Provider tours never appeared publicly in Prisma mode.** Tour list and detail were hard-coded to legacy tours.
- **Visibility bypass:** `?status=draft` and `?secretTour=true` could widen public tour results. Visibility is now an AND clause that query parameters can't override.
- **Error handler** hung requests when `NODE_ENV` was unset, and logged noise.
- **UI fixes:**
  - prices were shown with a hard-coded `$`;
  - departure dates showed a time and could shift a day;
  - the quantity field said "Sold out" before a departure was chosen;
  - the browser tab title was "Vite + React + TS".

### Security review
- No secrets are tracked in the working tree:
  - `config.env`, `.env` and `.env.local` are git-ignored;
  - the only committed env file is `frontend/.env.production`, whose sole value is the public API URL.
- **Outstanding:** the historic Atlas credential must be rotated by the owner.
- CORS:
  - explicit allow-list from `FRONTEND_URL` and `CORS_ALLOWED_ORIGINS`;
  - localhost origins only outside production;
  - rejections return 403.
- Auth: JWT secret of at least 32 characters is enforced in production; httpOnly, Secure, SameSite=None cookies; auth rate limit.
- Payments:
  - amounts are always server-computed;
  - client-supplied amounts are ignored;
  - webhooks need valid signatures and are re-verified with Chapa;
  - webhook events are idempotent;
  - mock confirmation is blocked in production unless explicitly enabled.
- Authorization was **not** relaxed anywhere to make tests pass. Ownership suites cover cross-organization access.

### Tests and docs
- Added the `chapa` (44 checks) and `tour-visibility` (21 checks) suites, and a single runner (`npm test`). Totals are in [TESTING_REPORT.md](TESTING_REPORT.md).
- Documentation: README, plus deployment, environment variables, testing, known limitations, image credits and this audit.

## 5. Portfolio readiness

Once the database URLs are set on Render, the project is a credible portfolio piece:
- a real three-sided marketplace;
- a PostgreSQL schema with versioned migrations;
- a properly designed payment integration (verification-first, signed and idempotent webhooks, reconciliation, late-payment handling);
- inventory holds;
- 317 automated integration checks;
- honest documentation of its limits.

The main caveat for a demo is the Render free-tier cold start. Open the API URL about a minute before presenting.
